# implementation notes

the core is a pure function over evidence. nothing in `src/core.ts` touches
dns, the clock, the network, or policy. evidence arrives as a plain object;
`analyze()` returns a versioned result. `src/evidence.ts` gathers evidence
(resolvers and adapters) so the core can stay deterministic and testable.

## layout

- `src/schema.ts` — the versioned result format. signal names, scopes,
  evidence strengths with explicit meanings, and the four states:
  `signals_present`, `mixed_routing`, `contradictory`, `unknown`. unknown is
  a first-class answer, never flattened into a verdict.
- `src/stages/input-handling.ts` — syntax validation with no product-specific
  acceptance rules. the local part is never rewritten: no plus stripping, no
  dot removal, no case folding. the domain is lowercased for dns only, and
  a unicode domain is converted to its punycode form (a deliberate policy:
  dns and the lists are ascii-only; the local part is never touched, and a
  failed conversion is rejected honestly rather than mangled).
- `src/stages/domain-intelligence.ts` — known relay and disposable domain
  lists. emits domain-scope signals only.
- `src/stages/routing-intelligence.ts` — maps observed mx exchanges through
  the provider table into forwarding, mailbox-capable, gateway or shared
  categories. unknown infrastructure gets no category claim. gateways are
  never classified as forwarding-only. infrastructure shared by forwarding
  and mailbox products gets a dedicated shared_mail_infrastructure signal
  that makes no arrangement claim in either direction.
- `src/stages/address-analysis.ts` — alias syntax facts. the syntax
  observation and the known provider semantics are two separate signals and
  are never merged.
- `src/stages/aggregation.ts` — collects signals, downgrades stale
  intelligence to unresolved, reports contradictions, derives the state.
  it never says accept or reject.
- `src/providers.ts` — the intelligence tables. entries verified against
  live dns or official docs are marked; the rest need verified research
  before production use. matching is longest-match-wins, so exact hosts
  beat generic suffixes (consumer outlook is mailbox-capable; a tenant's
  exchange online protection host stays a gateway). relay domains come
  from service docs; the authoritative list for each masking service is
  its own dashboard.
  - staleness: table-derived signals are stamped with
    PROVIDER_TABLE_AS_OF and community-list signals with the snapshot
    date, so an unmaintained table stops producing claims on its own once
    older than maxAgeDays (default 90). refresh the verification and bump
    the date, or the intelligence expires.
  - known gaps, kept honest instead of guessed: porkbun's in-house hosted
    email product (inboxes plus 20 free forwards, plus a proton
    partnership) has no published mx hosts in text — only its forwarding
    hosts (fwd1/fwd2) are in the table; spaceship's forwarding product
    publishes no mx records in its knowledgebase, so a
    spaceship-forwarded domain reports unknown infrastructure; smtp.google.com
    (the current workspace single-host mx) and spacemail are in and verified.
- `src/generated/disposable-domains.ts` — a snapshot of the cc0 community
  blocklist (disposable-email-domains on github), generated by
  `npm run sync:lists`. its signals carry community-list provenance,
  separate from the curated seed. rerun the script periodically; that is the
  ongoing maintenance cost of the disposable list.
- `scripts/sync-disposable-list.mjs` — the maintenance script behind the
  generated list. it uses the network; the core never does.
- `scripts/build-corpus.mjs` + `docs/authorized-corpus.md` — the workflow
  that breaks the self-grading loop: labeled, authorized real addresses
  (ground truth written before running anything) are recorded with live mx
  and merged into the eval. fixture passes alone only ever proved
  consistency; failures on the authorized corpus are data (a wrong or
  missing table entry, or a documented coverage gap), never something to
  edit the corpus over.
- `src/adapters.ts` — the external intelligence boundary. adapters declare
  what data they receive; domain-only lookups are preferred so the local
  part never leaves the core. provenance is retained on every signal.
- `src/doh.ts` — mx resolution over dns-over-https, for environments where
  udp/53 is unavailable.
- `src/eval/` — the evaluation corpus and runner. corpus cases supply
  fixture evidence so the harness runs offline and deterministically.
  the fixtures and the tables share an author, so fixture passes prove
  consistency, not real-world accuracy — the runner says so on every run
  until data/authorized-corpus.json (gitignored) exists with authorized,
  verified real addresses, which it merges automatically. failure kinds are
  reported separately (false positives, false negatives, wrong states,
  missed limitations, scope overreach) and unknown-state results are their
  own rate, never folded into the failure count. overreach is checked
  generically: recognized address-scope signals from domain-level evidence
  are flagged on every case, not a hand-picked list. domain-only success
  is never counted as address-level coverage.

## privacy

results carry the domain only, never the local part. caching and logging of
raw addresses remain a deliberate open decision, per the contract.

## usage

```sh
npm install && npm test   # build, unit tests
npm run eval              # run the corpus
node dist/src/eval/cli.js someone@example.com   # live lookup via doh
```

as a library:

```js
import { analyze, gatherEvidence, makeDohResolver } from "themailtell";
const evidence = await gatherEvidence("user@example.com", {
  resolver: makeDohResolver(),
});
const result = analyze(evidence); // signals + state, never a verdict
```
